# MarkdownX (v2.4.1)

> 一款专为计算力学、材料科学及算法推导文档设计的高性能、极简 Typora 风格桌面 Markdown & LaTeX 编辑/排版应用。
> 采用 **Tauri v2 + Rust** 原生内核与 **React 18 + TypeScript + Vite** 前端架构，实现毫秒级启动与超低内存占用。
>
> 📘 **维护、发布、排查请看 [`MAINTENANCE.md`](./MAINTENANCE.md)** ——
> 项目结构、版本号同步清单、发布流程（一条命令）、自动升级机制与故障排查、文件关联的注册表位置、
> 必须保持的不变量、已知坑与验证方法论。

## 核心特性

- **纯正 Typora 沉浸式单栏排版**：默认采用居中出版级纸质版式（标准宽度 860px），优雅自适应留白，支持通过快捷键 `Ctrl + /` 或双击正文一秒在全屏沉浸排版与全屏源码编辑之间来回切换。
- **自主 AST 公式编号与交叉引用引擎**：在前端 AST 编译层自主管理 `\tag{...}` 与 `\label{...}`，彻底杜绝 MathJax 动态渲染中的 `(???)` 标签失效问题；正文中 `\eqref{...}` 自动生成交互式原生直链，点击可平滑滚动定位到对应公式。
- **参数级细粒度排版与字体系统**：
  - **字体族自由混搭**：西文字体族（Times New Roman、Cambria、Georgia、Garamond、Segoe UI、JetBrains Mono、Fira Code）与中文字体族（思源宋体/SimSun、微软雅黑/苹方、楷体、仿宋）独立选择。
  - **段落与间距全控制**：正文字号（12~26px 滑块无级调节）、行高（1.4~2.5）、段间距自由调节。
  - **对齐与缩进规范**：支持两端对齐（末行强制靠左，杜绝尾行拉伸空白）与自然左对齐切换；支持正文首行缩进 2 字符。
  - **版心自适应宽度**：支持 760px（窄版）、860px（标准）、1020px（宽版大图）、1280px 及 100% 全屏自适应。
  - **偏好永久记忆**：所有排版选项自动持久化存储于本地。
- **工作台界面与文档管理**：
  - 顶部极简标题栏：文档名与未保存标记、`排版 / 源码` 视图切换、线性图标微操作簇（撤销/重做/剪切/复制/粘贴）、专注模式、排版检查器、主题与帮助。
  - 菜单（`⋯`）收纳文件、视图、主题与帮助全部命令；侧栏提供 `＋新建文档` 强入口、全文查找替换、已打开文档与工作区文件树。
  - 侧栏大纲为**可逐节点折叠的层级树**（父节点插入符独立于折叠态），点击即跳转对应标题。
  - 支持历史打开文件（Recent Files）快捷访问与清空。
- **大 M 艺术体全新视觉体系**：配备精心设计的大 M 艺术体（Artistic M）全套桌面多尺寸高分辨率图标及 `.ico` 资源，界面顶栏与侧栏均统一嵌入品牌 Logo。
- **主题跟随系统 (Auto)**：默认按操作系统配色实时切换（系统浅色 → 纯白学术，系统深色 → 极客深色），亦可手动锁定 经典纯白 / 夜间极客 / 羊皮纸原木；浅色与原木为卡片式纸张，深色为近黑画布直书。
- **右侧排版检查器**：对齐方式、首行缩进、正文字号、行高、段间距与版心宽度实时调节，一键恢复默认。
- **科学计算代码高亮**：原生内置 `highlight.js`，针对 Fortran、C++、Python、JSON 等工程计算语言深度调优。
- **文本绘图引擎（Text-to-Diagram）**：原生集成 `mermaid`，在 Markdown 中以 ` ```mermaid ` 围栏直接绘制流程图、时序图、状态图与甘特图，完全离线可用，自动适配纯白/深色/原木三套主题；语法出错时优雅降级为可读源码。

### [v2.3.7] - 2026-10-07

#### 性能：大 PDF 内存占用修复（页面虚拟化）
- **根因**（CDP 实测）：PDF 查看器打开时把**所有页一次性栅格化**为 canvas。120 页文档 →
  120 个 canvas、约 3.76 亿设备像素、**≈1.4 GB 位图**常驻 WebView2 GPU 进程（工作集 1046 MB）；
  而 JS 堆仅 25 MB —— 是 canvas 位图内存，不是脚本。
- **修复**：页面**虚拟化**。只栅格化视口附近的页（前后各 1 页），滚出范围的页立即释放
  canvas 位图（`width=height=0`）与文本层 DOM。页面尺寸仍全量测量（廉价），滚动条高度与布局不受影响。
- **实测效果**（120 页 PDF）：GPU 进程 **1046 MB → 98 MB**，canvas 位图 **1433 MB → 24 MB**，
  DOM 节点 10427 → 869。滚动验证：进入视口的页正确渲染、滚走的页释放、无空白页、内存恒定。
- **打印**：改为逐页临时渲染到 scratch canvas（约 144 dpi），峰值内存降到单页，且不再依赖屏幕上已渲染的页。

### [v2.3.6] - 2026-10-07

#### 修复 PDF 打印「一页正常、一页空白」
- **根因**：打印时每页图像用 `width:100%; height:auto`。只要图像的纵横比**比纸张高一丁点**
  （画布尺寸取整，或 PDF 中某页尺寸与第一页不同），图片就会溢出当前页，多出一个几乎空白的
  sheet —— 于是呈现"正常、空白、正常、空白"。
- **修复**：每页图像改用**严格小于页面的盒子**（各边留 0.3mm）配合 `object-fit: contain`，
  无论纵横比如何都不会溢出；0.3mm 边距在成品上不可见。
- **验证方式**：在真实打印管线中离线复现（3 页内容 → 打出 6 页），应用修复后同一用例回到 3 页。

### [v2.3.5] - 2026-10-07

#### 修复 PDF 打印空白页
- **根因**：打印内容与**应用自身的打印样式表**（A4 的 `@page`、body 默认边距、界面元素的隐藏规则）
  相互干扰，导致出现空白页 / 首张空白。
- **修复**：PDF 打印改为写入一个**隐藏 iframe 的独立文档**再打印 —— 该文档只含
  `@page { size: <PDF 实际纸张> }`、`margin: 0` 与每页一张图像，应用 CSS 完全无法触及。
- 打印前**等待所有页面图像解码完成**（并留 5 秒兜底），避免"图未画好即打印"的空白。
- 输出：一页 PDF 一版、按 PDF 自身纸张尺寸、不含任何界面元素。

### [v2.2.2] - 2026-10-06

#### 引导版：更新源改用 raw 分发 + 发布走 GitHub API

**为什么以 raw 为主、Release 为备**
本机（= 应用所在网络）实测两种路线**都能用**，差别在依赖与速度：

| 路线 | 实测 | 是否依赖 github.com 前门 |
|---|---|---|
| raw（`release-assets` 分支） | 清单 0.42s / 包 1.76s，**0 次跳转** | **否** ✓ |
| GitHub Release | 清单 1.28s（2 跳）/ 包 2.84s（1 跳） | **是** ✗（该主机在本网络时通时断：曾测得 12s 超时/连接重置） |

更新检查按设计是**静默**的：若某个宿主当时不可达，表现就是"自动升级不触发"而没有任何提示。
因此 `plugins.updater.endpoints` 配成**两条按序尝试**（raw 优先、Release 兜底），
两种路线都会在每次发布时一并更新：

```
更新清单: https://raw.githubusercontent.com/callyli00/MarkdownX/release-assets/latest.json
安装包:   https://raw.githubusercontent.com/callyli00/MarkdownX/release-assets/MarkdownX_x.y.z_x64-setup.exe
```

- 两个文件放在专用分支 `release-assets`（**每次发布覆盖**这两个文件，`main` 保持干净；
  分支上每次覆盖会留下一个提交，属正常，可定期清理）
- 发布经 `gh`（走 api.github.com ✓）完成，**发布后脚本自动 curl 实测这两个地址** ✓
- 同时也会创建 GitHub Release（标签、发布页、订阅、CDN 资产），供人查看与作为兜底端点 ✓
- **我方案的代价**：raw 那份文件进 git 历史，每版约 +5.6 MB ✗（Release 的资产不占仓库 ✓）

**发布一条命令**（已实测可用 ✓）
```bash
node scripts/release-update.mjs --owner callyli00 --repo MarkdownX            # 签名打包 + 生成 latest.json
node scripts/release-update.mjs --owner callyli00 --repo MarkdownX --skip-build --publish   # 上传并实测
```

**许可证**：统一为 **Apache-2.0**（与仓库 LICENSE 一致；此前应用内误写 MIT ✗）。

**本版是"引导版"**：需手动安装一次；从它开始，后续版本可在应用内检查更新并一键升级。

### [v2.2.0] - 2026-10-04

#### 自动升级（方案 A：GitHub/HTTPS + 官方 updater 插件）

**用户选定的策略**：应用**检查**更新，**由用户决定**是否安装，**不做回滚**。

**工作方式**

| 环节 | 行为 |
|---|---|
| 启动后 | 延迟 20 秒**静默检查**一次；**不弹窗**、不打断阅读 |
| 发现新版本 | 只在顶栏**帮助图标上点一个小圆点**，菜单里显示「检查更新（有新版本 vX.Y.Z）」 |
| 用户点开 | 弹窗显示 新版本号 / 更新说明 / 当前版本 |
| 用户点「下载并安装」 | 下载 → **minisign 签名校验** → 静默安装（`installMode: passive`，保留安装位置与文件关联）→ 自动重启 |
| 任何失败 | **静默跳过并记日志**；绝不阻塞启动、不打断编辑 |
| 手动检查 | 帮助菜单 →「检查更新…」；无新版本时明确回「已是最新版本」 |

**一次性配置（需要你做）**

### [v1.9.14] - 2026-10-04

#### 一、根因修复：CRLF 文档中"第一个代码块之后公式全部不渲染"
- **症状**：Windows（CRLF）文档若同时包含**代码围栏**与公式，第一个代码块之后的公式全部不被识别，
  在预览里保持 `$$\ldots$$` 原文。
- **定位过程**：本地用 LF 测试文档始终无法复现；改为**同时测试 LF 与 CRLF** 后立即暴露：
  | 文档换行符 | 渲染结果 |
  |---|---|
  | LF | 120 节 → 120 条行间 + 240 条行内公式，全部正常 |
  | **CRLF** | **仅第 1 节正常，之后公式全部保持原文** |
- **根因**：`maskVerbatimRegions` / `extractMermaidBlocks` 用
  `/^[ \t]{0,3}(`{3,}|~{3,})[ \t]*$/` 判断**代码围栏结束行**，但 CRLF 下该行是 `` ```\r ``，
  `[ \t]*$` 匹配不到 `\r` → 判定为"未闭合围栏" → **从第一个代码围栏到文末全部被遮蔽**。
  遮蔽是长度保持的（正文照常显示），但这段内容对公式/引用 tokenizer **完全不可见** →
  代码块之后的公式一律不被识别。
- **修复**：三处围栏正则加 `\r?` 容错（`... [ \t]*\r?$` 与 `(.*?)\r?$`），**保持长度不变**，
  因此源码偏移映射不受影响。
- **影响面（实测）**：扫描用户文档库 2196 个 md 文件，命中该特征者仅 5 个（且其中 4 个只有行内公式）。
  即**这是一个真实但窄的缺陷**：需要"代码围栏 + 围栏之后还有公式"两个条件同时成立。
- **注意（结论更正）**：该缺陷**不是**"检测到 174 个公式未排版"的原因。那次现象的横幅统计的是
  "公式容器存在但没有 `mjx-container`"，属于**排版会话未执行**，与 v1.9.7–v1.9.12 的排版改造同源；
  该改造已于 v1.9.13 回退。

#### 二、解析搬入 Web Worker
- `renderMarkdown` 拆为 `renderMarkdownPayload`（Worker 安全：不做宿主相关的资产改写）+
  `finalizeAssetUrls`（主线程执行，需要 Tauri 的 `convertFileSrc`）；`renderMarkdown` 语义不变。
- 新增 `src/utils/renderWorker.ts`（Worker 入口）与 `src/utils/renderClient.ts`（主线程客户端）。
  文档 ≥ 20 KB 走 Worker，小文档保持原同步路径（避免无谓开销）。
- **纯优化层原则**：Worker 缺失/加载失败/抛错/超时，一律自动回退同步解析 ——
  **只可能变慢，不可能不渲染**。同时补"只提交最新请求"的守卫，避免异步乱序覆盖新内容。
- 实测：41,872 字符 CRLF 文档 → Worker 已加载、公式 120/120、主线程 2.24s 内 163 次 tick 不卡；
  将 `Worker` 置为 `undefined` 后同样 120/120（证明回退有效）。

#### 三、新增护栏 `tools/render-equivalence-gate`
- 证明 **Worker 路径 ≡ 同步路径（逐字节）**，并比对历史黄金文件（6/6 PASS）；
- 新增**换行符等价性**检查：同一文档的 LF 与 CRLF 变体必须渲染出相同结构（6/6 PASS）；

  不影响任何渲染/排版逻辑）。
- **局部渲染的新方向**（重新设计，尚未实现）：
  1. **优先用 CSS 解决**：对顶层块启用 `content-visibility: auto` + `contain-intrinsic-size`
     —— 浏览器自动跳过屏幕外块的布局与绘制，零 JS、零渲染语义变化，失败模式只是"效果打折"；
  2. **把解析移出主线程（Web Worker）**：窗口不再冻结、进度可见，而渲染产物与今天保持
     逐字节一致（可用护栏验证），排版仍走既有的整篇可靠路径；

### [v1.0.2] - 2026-09-26

#### 生产环境 (Build Release) 关键修复
- **修复 Release 构建后本机图片无法渲染问题**：
  - 在 `src-tauri/Cargo.toml` 中显式启用 `tauri = { version = "2", features = ["protocol-asset"] }` 特性。Tauri 默认在 release 编译时未开启资产协议特性，导致 `convertFileSrc` 生成的协议路由未在 WebView 注册。
  - 在 `src-tauri/tauri.conf.json` 中配置 `app.security.assetProtocol` 作用域为 `["**"]`，并在 CSP `img-src` 中加入 `http://asset.localhost` 与 `asset:`，确保 Windows 与 Linux 生产包中的本地图片资源正常加载。
  - 增强相对路径图片规范化（自动处理 `./`、盘符与分隔符）。
- **修复生产包初次启动时公式显示错误问题**：
  - 解决生产环境下本地界面瞬间挂载与远程 MathJax 异步加载的时钟时序竞争（Race Condition）。在开发模式下由于 Vite 启动耗时掩盖了此问题，而在生产包中页面 5ms 极速就绪时 MathJax 仍在网络请求中，导致首屏排版跳过。
  - 在 `index.html` 中引入 `MathJax.startup.ready` 钩子并在就绪时广播 `mathjax-ready` 规范事件；在 `markdownRenderer.ts` 中加入异步轮询等待，确保生产环境启动时公式 100% 自动就绪并排版。

## 软件发布与编译构建指南

### 1. Windows 环境编译（输出独立 `.exe` 及安装包）
在 **Windows PowerShell** 中运行：
```powershell
cd MarkdownX
pnpm install
pnpm tauri build
```
产物位置：
- 安装包：`src-tauri/target/release/bundle/nsis/MarkdownX_1.8.8_x64-setup.exe`

cd MarkdownX
pnpm install
pnpm tauri build
```
产物位置：
- `src-tauri/target/release/bundle/deb/markdown-x_1.8.8_amd64.deb`
- `src-tauri/target/release/bundle/appimage/MarkdownX_1.8.8_amd64.AppImage`

在 **macOS 终端** 中运行：
```bash
cd MarkdownX
pnpm install
pnpm tauri build
```
产物位置：
- `src-tauri/target/release/bundle/dmg/MarkdownX_1.8.8_universal.dmg`
